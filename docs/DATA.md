# Data: Docenda

> **v0.1 (17/11/2026). Planned: there is no code yet.** Turns the [DOMAIN](DOMAIN.md) into tables. Each slice's specification may adjust a detail; when it does, it fixes this file in the same PR.
> Based on: decisions [0004](decisions/0004-postgresql.md) (PostgreSQL 18), [0008](decisions/0008-ai-job-queue-postgresql.md) (queue and reservation), [0010](decisions/0010-logs-monitoring-and-incident-response.md) (records) and [0012](decisions/0012-transactions-repositories-and-module-layout.md) (owner, transaction and database roles).
> Siblings: [CONTRACTS](CONTRACTS.md) (what goes in and out through the API) and [ACCEPTANCE](ACCEPTANCE.md) (how to know each slice is done).

## 1. Conventions

| Subject | Rule |
|---|---|
| Names | In the database, singular `snake_case` (`lesson_plan`). In code, `camelCase`, with the mapping done in the Prisma schema (`@map`). Names come from the DOMAIN glossary |
| Identifier | `uuid` generated by the database with `uuidv7()` (0004). Never a sequential number |
| Time | `timestamptz`, always in UTC. Every table has `created_at`; those that change have `updated_at` |
| Money | `bigint` in nano-dollars (INV-12). No `numeric`, `float` or `money` column |
| Closed list | PostgreSQL `enum` type, with the English values from the DOMAIN. A new value is a migration |
| Text | `text`. The maximum size is checked at the edge, by the schema in [CONTRACTS](CONTRACTS.md), not in the database |
| `jsonb` | Only for what changes shape: plan content, context snapshot and the approved version. Every `jsonb` carries `schemaVersion` |
| Owner | Every author-resource table has `owner_id`, with a foreign key to the user |
| Between modules | Foreign keys only to the user and to the catalog (0012 D6). Any other link between modules is a `uuid` without a foreign key, and the owner module is called through its front door |
| Schema | Everything in the `public` schema; pg-boss lives in the `pgboss` schema |

## 4. What in the database guarantees each invariant

| Invariant | Database mechanism |
|---|---|
| INV-01 owner | `owner_id` required on every author table; an index starting with `owner_id` |
| INV-02 only catalog skills | Foreign key `plan_skill.skill_id` → `skill` |
| INV-04 the AI does not write to the plan | The worker uses a repository that only has `suggestion` and `ai_generation`; `lesson_plan.content` only changes through the author's actions |
| INV-05 one active generation per plan | Partial unique index on `ai_generation` |
| INV-06 balance and cap | `SELECT … FOR UPDATE` on `credit_account` and on `ai_budget_period`, inside the reservation transaction |
| INV-07 cost never lower than the actual | Without `settle`, the whole reservation stays; `settle` is unique per generation |
| INV-08 nothing runs forever | `deadline_at` and the sweep index |
| INV-09 identification kept out of the AI | `plan_identification` is another table, read by another method |
| INV-12 money as integer | `bigint` only |
| INV-13 prompt, model and effort | `NOT NULL` on the three columns |
| INV-14 audit only grows | Permissions of the `docenda_app` role (section 5) |
| Immutable approved version | `docenda_app` without `UPDATE` on `lesson_plan_version` |

INV-03, INV-10 and INV-11 are guaranteed in the code (pure approval function, pipeline step and job type), not in the database.

## 5. Roles and permissions (0012 D5)

| Table | `docenda_app` (API and worker) | `docenda_retention` (cleanup jobs) |
|---|---|---|
| `audit_event`, `access_record` | Insert and read | Delete what has expired |
| `lesson_plan_version`, `credit_entry`, `deletion_receipt` | Insert and read | — |
| `curriculum_framework`, `skill` | Read | — |
| All the others | Read, insert, update and delete | — |

- The catalog is only written by the import command, which runs as `docenda_owner` along with the migrations.
- Deleting a plan or an account removes the child rows by `ON DELETE CASCADE`. In PostgreSQL this action runs with the table owner's permission, so `docenda_app` does not need `DELETE` on `lesson_plan_version` or on `credit_entry`. **To be confirmed with a test in F06.**

## 6. Deletion and retention

What happens to each table when the account is deleted, side by side with section 7.1 of REQUIREMENTS.

| Table | On account deletion | How |
|---|---|---|
| `user`, `session`, `account`, `verification`, `terms_acceptance` | Deleted | User row deleted; the others by cascade |
| `class_context`, `lesson_plan` and everything hanging from it, `source` | Deleted | `ON DELETE CASCADE` from `owner_id` |
| `credit_entry`, `credit_account`, `misuse_occurrence`, `misuse_block` | Deleted | Cascade |
| `ai_usage_record` | **Anonymized** | `ON DELETE SET NULL` on `user_id` |
| `ai_budget_period` | Stays | Has no link to a person |
| `access_record`, `audit_event` | Stay up to 6 months | No foreign key; the retention job deletes them |
| `deletion_receipt` | Stays | Identifies nobody |
| pg-boss jobs | Nothing to delete | They carry IDs only and disappear in 1 day (0008 D6) |

Deletion is **by construction**: once the user row is deleted, the database leaves none of their content behind. A test checks that no author table has an `owner_id` without cascade.

Scheduled cleanups (pg-boss jobs):

| Job | Frequency | Deletes or changes | Role |
|---|---|---|---|
| Orphaned generations | Every minute | Closes as `failed` and `worker_lost` | `docenda_app` |
| Expired invitations | Daily | `status = expired` and e-mail deleted | `docenda_app` |
| Accounts deactivated for more than 30 days | Daily | Deletes the account (table above) | `docenda_app` |
| Accounts idle for 6 months | Daily | Warns by e-mail and deactivates | `docenda_app` |
| Audit and access records older than 6 months | Daily | Deletes | `docenda_retention` |
| Misuse occurrences older than 90 days (proposal) | Daily | Deletes | `docenda_app` |

## 7. Modelling decisions

Made while writing this document, on 17/11/2026, within what decisions 0001 to 0014 already allowed.

| # | Decision | Reason |
|---|---|---|
| D1 | Account deletion by database cascade, not by a list of `DELETE` statements in the code | Code forgets a new table; a foreign key does not |
| D2 | Plan identification in a separate table | The AI query has no way to bring it in by mistake |
| D3 | The identification stays out of the approved version | Changing the lesson date should not reopen the plan |
| D4 | The week's workload, exam week and the teacher's opinion live in the plan, not in the saved context | The context is reused for months; "exam week" applies to one lesson |
| D5 | `class_size` in the context | The rubric checks whether the activities fit the class, and that needs a number |
| D6 | Text with a privacy alert is not stored without a fix or a confirmation | "No student data stored" becomes a rule of storage, not just a warning |
| D7 | A replaced pending suggestion is deleted, not flagged | It was never decided; keeping it serves no one |
| D8 | Plan template and domain list as versioned data files | In v1 only the developer changes them; a table would call for an admin screen |
| D9 | The month's cap read from `setting` at reservation | Changing the cap applies on the next request (RF-75) |
| D10 | Reservation and settlement unique per generation, by index | A worker retry does not charge twice |
| D11 | `revision` on the plan | Autosave in two tabs does not silently lose text |
| D12 | Deleting a plan with an active generation is refused | Avoids a reservation with no owner and a worker reading a plan that disappeared |
